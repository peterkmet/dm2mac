# Dungeon Master II C port: PRD

## Goal

Produce a native macOS port of Dungeon Master II: The Legend of Skullkeep (PC DOS, English, 1995) in C11 with SDL3. The C code is a readable reimplementation of the game code in `SKULL.EXE`. It is derived from our own Ghidra decompilation. The port is not an emulator.

The port gives the best quality of the PC version: VGA graphics with 256 colors, digital sound effects, and FM music.

## Reader

This PRD is for the developer and the agents that write the implementation plan and the code.

## Scope

In scope:

- The game in `SKULL.EXE`: from the start menu to the end of the game.
- Graphics, digital sound, and FM music.
- Save files in the original format.
- Upscaling (Scale2x, Scale3x) as in the Dungeon Master port.

Out of scope for this PRD:

- Intro, ending, and credits (`INTRO`, `END`, `CREDITS`, `FTL`, `SPLASH`). A separate PRD covers them later.
- Additions that the original does not have: automap, LLM control mode, turn-based mode. A separate PRD covers them later.
- Sound card selection, `SETUP.EXE`, `skull.cfg`, DOS/4GW, HMI drivers as drivers.
- Other platforms than macOS.

## Source version

- Base: PC DOS version, English. The files are in `Dungeon Master II for PC English/`.
- `SKULL.EXE` is a 32-bit LE executable for DOS/4GW. The compiler is Watcom C/C++32. Watcom passes arguments in registers (EAX, EDX, EBX, ECX), then on the stack.
- Data files: `DATA/GRAPHICS.DAT`, `DATA/DUNGEON.DAT`, `DATA/SONGLIST.DAT`, `MELODIC.BNK`, `DRUM.BNK`.
- The game reads saves `SKSAVE*.DAT` and `SKSAVE*.BAK`.
- Music is FM only (`README.TXT`: "DM2 supports FM music only").

## Decisions

| Topic | Decision |
|---|---|
| Repository | Standalone repository `dm2/`. No dependency on `../dm`. Tools and rules from `../dm` are copied and adapted. |
| Game files | Move to `game/`. `game/` is git-ignored. No game content in git. |
| Disassembly | Own LE loader in Python (`dm2-le`). It applies the fixups and writes a flat memory image. Ghidra imports the image as raw binary `x86:LE:32`. Unicorn loads the same image. |
| Test oracle | Unicorn (x86 CPU emulator), for tests only. The harness calls original functions with the Watcom register convention. |
| Language and build | C11, `clang`, plain `Makefile`, SDL3 from Homebrew. No CMake. |
| Code style | `docs/coding-standard.md`, copied from `../dm` and adapted for x86. New code follows it from the first step. |
| Saves | Same format as the original. The port reads DOS saves. The DOS version reads port saves. |
| Screen | Internal framebuffer 320×200, 8 bits per pixel, 256-color VGA palette. Window with scale 3. Optional Scale2x or Scale3x filter. |
| Music | Nuked-OPL3 (one C file, LGPL-2.1, license file in the repository). Own HMP and BNK player. |
| Reuse of other projects | ReDMCSB, SKWin, reDM2 (https://codeberg.org/CyCl0ne/reDM2), and similar projects may be read and cited for names, data formats, game logic, and test methods. Do not copy their code 1:1. Cite the source in a comment when the port follows their analysis. |

## Stages

1. Tools: LE loader, Ghidra headless decompilation, Unicorn oracle.
2. Code map: classify the functions of `SKULL.EXE` by subsystem. Give names and signatures in `docs/skull-symbols.csv`.
3. Data layer in C: `GRAPHICS.DAT`, `DUNGEON.DAT`, save format.
4. Platform layer: SDL3 window, palette, upscaling, input, digital sound, OPL3 music.
5. Game logic by subsystem: dungeon view, interface, movement, timeline, champions, items, creatures, magic, and the systems that are new in DM2.
6. Start menu, save and load, end of game, full test, release.

The implementation plan defines the exact steps.

## Epics

### Epic 1: Tools

```gherkin
Feature: Load and decompile SKULL.EXE
  Scenario: Make a flat memory image
    Given SKULL.EXE in game/
    When I run "uv run dm2-le game/SKULL.EXE build/skull.bin"
    Then the tool writes a flat memory image with all fixups applied
    And the tool prints the base address of each object and the entry point

  Scenario: Decompile the image
    Given the flat memory image
    When I run the Ghidra headless script
    Then decomp/SKULL.c contains C code for each function
    And the functions have the names from docs/skull-symbols.csv

  Scenario: Call an original function
    Given the flat memory image
    When a test calls an original function through the Unicorn harness with register arguments
    Then the harness returns EAX
    And an access to an I/O port, an interrupt, or a DOS/4GW call stops the call with an error
```

### Epic 2: Data layer

```gherkin
Feature: Read the game data
  Scenario: Decode all images
    Given GRAPHICS.DAT in game/DATA/
    When the C port decodes each image
    Then each image is equal to the result of the original decode function in the Unicorn harness

  Scenario: Load the dungeon
    Given DUNGEON.DAT in game/DATA/
    When the C port loads the dungeon
    Then the map count, the map sizes, and the object counts are equal to the values that the original loader gives

  Scenario: Read and write a save
    Given a save from the DOS version
    When the C port loads the save and writes it again
    Then the written file is equal to the original file
```

### Epic 3: Platform layer

```gherkin
Feature: Show the game on macOS
  Scenario: Start with a filter
    Given the game files in game/
    When I run "build/dm2 --filter scale2x"
    Then a window opens with the game image at scale 3
    And the image uses the Scale2x filter

  Scenario: Play sound effects
    Given the game runs
    When an event in the game plays a sound
    Then the sound plays with the volume and stereo position that the original code calculates

  Scenario: Play music
    Given the game runs in a place with music
    When the game starts a song from SONGLIST.DAT
    Then the HMP player plays the song through the OPL3 emulation with the instruments from MELODIC.BNK and DRUM.BNK
```

### Epic 4: Game logic

```gherkin
Feature: Play the game with the original rules
  Scenario: Random numbers
    Given the same random seed
    When the C port and the original code generate 1000 random numbers
    Then the two sequences are equal

  Scenario: Scenario from a DOS save
    Given a save from the DOS version
    And a sequence of commands
    When the C port runs the commands
    Then the party position, the champion state, and the creature state are equal to the expected state

  Scenario: Systems that are new in DM2
    Given the code map lists outdoor areas, weather, day and night, shops, money, minions, and Skullkeep machines
    When the C port implements each system
    Then each system has at least one automated test
```

### Epic 5: Complete game

```gherkin
Feature: Play from start to end
  Scenario: New game
    Given the game files in game/
    When I start build/dm2 and select a new game
    Then I can recruit champions and enter the game

  Scenario: Save and load
    Given a game in progress
    When I save, quit, start again, and load
    Then the game continues in the same state

  Scenario: End of game
    Given a save near the end of the game
    When I complete the final task
    Then the game shows the end sequence of SKULL.EXE
```

## Fidelity rules

- Game rules follow the decompiled code exactly: random numbers, timeline, movement, combat, magic, creature AI, and new DM2 systems.
- The view uses the drawing order and the coordinate tables of the original.
- The main loop runs at the tick rate of the original timer (PIT). The port derives the tick from the SDL timer.
- The port does not reproduce the DOS technical layer: DOS/4GW, memory manager, image cache, HMI drivers, direct VGA register access, Mode X, and busy waits for vertical retrace.
- Original bugs that change what the player sees or plays stay. Clear technical bugs (overflow, uninitialized values) are fixed. A short comment marks each fix.
- The original uses 32-bit `int`. Use `int16_t` or `uint16_t` only where the original uses a 16-bit value.
- The data files are little-endian. Read them with explicit byte order.
- The game reads all game data at run time. The source does not contain copies of game tables.

## Testing

- `uv run pytest` is the only test runner. The C port builds as `build/libdm2.dylib`. Tests call it through `ctypes`.
- Each plan step adds at least one automated test.
- Test types:
  1. Tool tests: the LE loader on a small synthetic LE file, and the known entry point and strings in `SKULL.EXE`.
  2. Differential tests: pure functions get the same input in C and in the original code in Unicorn. The results must be equal.
  3. Data tests: image decoding and dungeon loading against the original code.
  4. Scenario tests: a DOS save plus a command sequence gives the expected state.
  5. Music tests: the HMP player renders a short part of a song. The output is not silent, and the event timing is equal to the HMP file.
- Tests that need `game/` skip when `game/` is missing. Saves from DOSBox are in `tests/saves/` and are git-ignored.
- Manual check (workflow step 6): compare the port with the DOS version in DOSBox side by side. Check image, sound effects, music, and input.

## Command line

| Option | Default | Effect |
|---|---|---|
| `--data DIR` | `game` | Folder with the game files. The game writes saves to this folder. |
| `--filter NAME` | `none` | Upscaling filter: `none`, `scale2x`, `scale3x`. The `DM2_FILTER` environment variable sets the same value. |

## Open points for the analysis

These points do not need a decision from the user. The analysis in stages 1 and 2 answers them and records the answers in `docs/`.

- The format, sample rate, and channel count of the digital sounds.
- The location of the HMP songs (probably in `GRAPHICS.DAT`).
- The effect of the SVGA install option. The port implements the SVGA mode only if it gives a better image.
- The purpose of `DUNGENB.DAT` and `GRAPHIC2.DAT`, which `SKULL.EXE` names but the folder does not contain.
- The MIDI to OPL conversion of the HMI driver. If `HMIMDRV.386` cannot be decompiled, the player uses a standard AdLib conversion.

## Success criteria

- `make -C port` builds `build/dm2` and `build/libdm2.dylib` without warnings.
- `uv run pytest` passes.
- A player can play from a new game to the end of the game on macOS.
- The image, sound effects, and music match the DOS version in DOSBox.
- A save from the DOS version loads in the port. A save from the port loads in the DOS version.
